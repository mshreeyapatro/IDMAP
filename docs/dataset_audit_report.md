**Important open question:** the numeric filename prefix (e.g. `35`) is currently the only grouping key available, and it is what `event_labels.csv`'s `label` column reproduces. It is unclear from the data alone whether this numeric ID identifies a distinct **cyclone event** (storm) or just a **photo/sequence number** with duplicate quality variants. This must be confirmed (with the mentor or original data source) before doing event-wise train/val/test splitting, since the SRS's leakage-mitigation strategy depends on splitting by real cyclone identity, not by image-sequence number.

**Update (source traced, no per-image labels found):** `event_labels.csv` was confirmed identical to `insat_3d_ds - Sheet.csv`, downloaded from a Kaggle notebook, "Cyclone Intensity Estimation using INSAT Imagery" (kaggle.com/code/rahulkonda18/cyclone-intensity-estimation-using-insat-imagery). That notebook's own training code uses this same meaningless group-index column as its regression target (`y_col="label"`) -- which is why its reported result is a negative R² (-1.077, worse than predicting the mean): the "label" was never a real intensity value. The notebook's data-loading path reveals the images' origin: a separate underlying Kaggle dataset named **`insat3d-infrared-raw-cyclone-images-20132021`**, implying the collection spans cyclones from **2013 to 2021** -- a real, if coarse, piece of context. That source dataset's own page has not yet been checked for a fuller description/citation; worth checking before concluding no timestamp/storm-identity data exists anywhere upstream.
